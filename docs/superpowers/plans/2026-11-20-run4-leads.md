# Run 4: People and leads, then "it comes to you" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Leads as people with a lead status (Part A), a monthly "What it caught" report (B), email logging by BCC (C),
a phone notification at brief time (D) and install-doc housekeeping (E), each task its own PR.

**Architecture:** A lead is a `contacts` row with `lead_status`; every lead write is one audited change through the
existing service layer (`commitChange`), shared by MCP tools and board forms. Rules gain `lead_followup` (the engine
stays pure). B is a pure compose function plus a loader. C is the Worker's `email()` handler. D is a no-payload web
push signed with VAPID through Web Crypto, and a service worker that only shows a fixed notification.

**Tech Stack:** Cloudflare Workers, D1, Email Workers, Web Push (VAPID, RFC 8292), TypeScript run by Node type
stripping, `node:test`, the existing D1 shim over `node:sqlite`, `wrangler dev --local` for e2e.

**Spec:** `docs/SPEC.md` (updated for run 4), `docs/decisions/0022-leads-on-contacts.md` (Part A, binding), and the
owner's brief `.owner-review/run4-brief.md` (git-ignored copy; parts B to E, quality bar, end of run). Read all three.

## Global Constraints

- One branch and PR per task, from a fresh `main` (`git switch main && git pull --ff-only`). TDD. `npm run check`
  before every commit. Never commit to `main`, never `--no-verify`, never `[skip ci]`.
- Every write is one audited change (`commitChange`) with a one-line summary ending `(change chg_…)`; undo works on
  each new kind of change (test one undo per new service).
- Outside text stays labelled (`untrusted_text`, `untrusted_fields`); summaries, headlines and errors name people
  only through `src/services/labels.ts`.
- Fake people only, at `example.com`, `example.org`, `example.net` or `example.test`.
- Board: one `<h1>`, landmarks, 44 px targets, the `html` tag only, colours only from `public/board.css` tokens, works
  at 375 and 1280 px, every action works without JavaScript, `public/*.js` at most 3 KB gzipped each, no fetch or
  innerHTML in board scripts.
- Lead status keys are exactly `new`, `contacted`, `not_now`, `not_a_fit`, `bad`, `qualified`; labels New, Contacted,
  Not now, Not a fit, Bad lead, Qualified. Unqualified = every key but `qualified`.
- Dependencies: exact pin, at least 7 days old (`npm view <pkg> time`), installed with
  `npx --yes npm@10.9.9 install -E <pkg>@<version> --before=<7 days ago>`; flag each in the PR and the run summary.
- Never run `wrangler deploy`, `wrangler login`, `--remote`, or the copy scripts for real; secrets and DNS go to the
  STOP queue. Owner-only paths (`.github/workflows`, `.claude/**`) are proposals in the scratchpad only.
- A decision record for each judgment call (`docs/decisions/0023-…` onward, next free number at the time).
- New migrations take the next free number on `main` (0006 is leads); each gets a "from the previous version" test in
  `src/db/migrations.test.ts` with fake rows for every table, and new tables get `FAKE_ROWS` entries.

## Review Focus

1. **A person reached twice in one batch.** Logging a call on a `new` lead whose row another write just bumped must
   fail as a stale write, not silently skip the status move. Test (L2): log_activity on a lead after a concurrent
   update_contact answers "changed since you read it" and leaves the status as it was.
2. **Undo across the lead/deal line.** Undo of `qualify_lead` after an activity is logged on the new deal refuses in
   plain English; undo of `return_to_lead` after the person got another open deal refuses (the contact row changed).
   Tests: L3 `leads.test.ts`.
3. **Rule history on a lead.** Undo of `add_lead` after a `lead_followup` rule fired on that person refuses with what
   to do instead (mark them Bad lead or Not a fit), not "change those first". Test: L5 `undo.test.ts`.
4. **Messy business names and sources.** "  Acme  Plumbing " and "acme plumbing" are the same company for the
   duplicate check, the Leads source filter and the import dry run; an empty business never matches. Tests: L2
   (`addLead` duplicate), L6 (source groups), L8 (import "possible duplicate").
5. **Hostile mail and push endpoints.** A logged email with a spoofed From, a failed auth result, no Message-ID, 50 Cc
   addresses or a 2 MB body must not throw or log more than the caps; a push endpoint answering 410 is not tried again.
   Tests: C1 `email/log.test.ts`, D1 `push/send.test.ts`.
